# 1. 产品定义

## 1. 产品定义

## 1.1 产品名称

产品名建议为：**SmartLedgerLocal**

中文可理解为：

- 智能记账本
- 本地优先记账 App

## 1.2 产品类型

这是一个 **iOS 原生个人记账 App**，但不是只做"每天记一笔"的极简记账器，而是同时具备：

1. 普通日常记账
2. 主题账本归集
3. 预算管理
4. 多分类
5. 图片 OCR 导入账单
6. 分期消费拆分
7. 多人分账
8. Apple 原生账号与 iCloud 同步

## 1.3 产品核心价值

这个 App 的核心价值不是"账务严谨到企业财税级别"，而是：

- 让个人用户低门槛记录收支
- 能同时处理日常消费和主题型开销
- 能从截图直接识别账单，减少手输
- 能快速看周报、看趋势、看预算
- 不依赖自己部署服务器
- 在 Apple 生态里尽量原生、轻量、顺手

## 1.4 目标用户画像

目标用户是：

1. **个人记账用户**：想知道每月花了多少钱，想看餐饮、交通、购物占比。
2. **有专题消费归集需求的用户**：比如"三亚旅行""一次装修""某个节日""某段体检周期"，想把这类支出和收入集中管理。
3. **喜欢 Apple 原生体验的用户**：不想自己搭服务器，希望本地级体验，希望未来能用 iCloud 同步。

## 1.5 不做什么

为防止另一个 AI 误解方向，这里明确说不做：

1. 不做 web 前后端系统
2. 不要求自建后端服务器
3. 不优先考虑 Android / Windows 跨平台
4. 不做企业级财税报表系统
5. 不做证券、基金、资产组合管理系统

# 2. 开发边界与技术约束

## 2.1 平台要求

- 仅 iOS
- 最低建议：iOS 17+

## 2.2 技术栈要求

- **SwiftUI**：所有页面
- **Charts**：图表
- **Vision**：OCR 文本识别
- **PhotosUI**：图片选择、背景图选择
- **SwiftData** 或本地快照持久化 / 本地存储
- **CloudKit**：云同步
- **AuthenticationServices**：Sign in with Apple

## 2.3 架构原则

必须遵守：

### 原则 1：本地优先

所有新增、编辑、删除操作先写本地。

### 原则 2：云同步不是唯一数据源

App 即使不开启 iCloud，也必须完整可用。

### 原则 3：状态中心统一管理

建议有一个中心 Store / ViewModel 负责：

- categories
- books
- transactions
- budgets
- OCR 结果
- Dashboard 统计
- 同步状态
- Apple 账号信息

### 原则 4：原生交互优先

要像 iOS App，而不是把网页式交互硬塞进来。

# 3. 核心概念解释

## 3.1 流水

"流水"是最基础的记账单位，一条记录代表一笔收入或支出。

## 3.2 分类

分类是树结构，可多级，支持图标和颜色。父分类与子分类都可直接用作流水类别。

## 3.3 账本

这里的"账本"不是应用层面的总账，而是：

> 一个有名字、有主题、有时间范围、可自动归集流水的专题容器。

举例：三亚旅行、新家布置、春节回家、体检与看牙。

## 3.4 预算

预算是对一个分类或全部支出的金额上限约束，支持按月或按区间。

## 3.5 自动归集

当某条流水的时间和分类符合某个账本的归集条件时，该流水可以被推荐加入或自动加入该账本。

## 3.6 分期

分期并不是一条流水上挂一个标签，而是：

> 在存储层拆成多条按月发生的流水，并通过分期组 ID 关联。

## 3.7 多人分账

多人分账只在账本语境下成立，即：

- 某个账本开启了多人分账
- 账本定义了参与人
- 某笔流水可以指定付款人 / 分账成员

## 3.8 OCR 导入

OCR 导入不是"直接拦截截图变成流水"，而是：

1. 识别文字
2. 解析金额 / 商户 / 支付渠道 / 时间 / 分类建议
3. 让用户确认后再保存

# 4. 信息架构与导航结构

## 4.1 底部主导航

底部 Tab 一共 5 个：

1. 概览
2. 账本
3. 流水
4. 记账
5. 更多

## 4.2 "更多"中的二级入口

"更多"页面内再提供：

- 预算
- 分类
- 设置

## 4.3 导航切换行为

这是一个很重要但容易被忽略的交互细节。

### 要求

当用户切换底部导航栏时，当前功能页应该尽量回到该 Tab 的最外层。

### 设计目的

- 防止用户在分页 / 账本详情 / 编辑页里层层 push 后迷路
- 保持底部导航的"返回功能首页"感知

### 建议实现

每个 Tab 使用独立 `NavigationStack`，切换 Tab 可重置导航路径。

# 5. 全局视觉与交互原则

## 5.1 风格关键词

- 原生
- 简洁
- 轻玻璃感
- 半透明卡片
- 不花哨
- 可读性优先

## 5.2 主题模式

必须支持：

- 跟随系统
- 白天模式
- 夜间模式

## 5.3 背景图

支持用户自定义背景图。背景图存在时：

- 页面卡片尽量使用 `.ultraThinMaterial` 或半透样式
- 避免大量死白背景块
- 但文字必须保证看得清

## 5.4 卡片样式

建议统一使用玻璃卡片组件，例如：圆角 18~24、超薄材质背景。

### 5.4.1 识别性要求

分类和账本的视觉设计必须服务于"快速识别"：

- 用户看到图标和颜色时，应能快速分辨是餐饮、交通、购物、收入等大类
- 账本图标和颜色也应帮助用户一眼识别专题性质
- 不要把图标和颜色仅仅当作装饰

## 5.5 筛选器样式

所有胶囊按钮应保持统一：

- 选中态明显
- 未选中态轻柔
- 背景不突兀
- 白天 / 夜间都不刺眼

补充要求：

- 首页的周 / 月 / 年切换、分类占比筛选器、流水页的时间过滤和分类按钮，视觉风格要统一
- "全部分类 / 全部大类"这类按钮背景要柔和，不能像调试按钮那样突兀

## 5.6 图表视觉原则

- 图例简约
- 颜色一致
- 不要过度装饰
- 坐标与标签优先保证可读性

补充要求：

- 饼图与柱状图之间切换后，颜色映射必须保持一致
- 图例不应跟随滚动的图表一起移动
- 图例一行放不下时可自动分两行，但仍须简洁
- 流水日期、分组日期、次级信息在白天 / 夜间 / 背景图场景下都必须可读

## 5.7 文案原则

整体文案要简洁，避免在主流程里堆积教程式、注释式、开发说明式文字。

### 例外

以下场景可以保留必要说明：

- 自动归集风险提醒
- 云同步冲突说明
- OCR 识别置信度和识别来源说明
- 分期、预算等业务语义区域

## 5.8 App 图标与封面要求

用户明确强调软件封面 / App 图标需"家常小鲫鱼"气质，因此建议：

- 主色偏蓝色系
- 形象偏可爱、圆润、亲和
- 不要做成严肃商务风
- 保留"功能 / 钱包 / 账本"语义即可，不需要复杂细节

此项不是功能强约束，但应作为视觉方向说明给复现 AI。

# 6. 核心数据模型

以下是必须具备的模型含义，字段名可根据实现略调，但语义不能丢。

## 6. 核心数据模型

以下是必须具备的模型含义，字段名可根据实现略调，但语义不能丢。

## 6.1 FlowType

```
expense
income
```

分别表示支出和收入。

## 6.2 Category 分类模型

建议字段：

- `id`
- `name`
- `flowType`
- `icon`
- `color`
- `parentId`
- `level`
- `children: [Category]`

要求：

1. 是树结构
2. 支持多级
3. 父节点可直接作为流水类别
4. 子节点也可作为流水类别
5. 必须支持图标与颜色

### 父分类可直接使用的特殊语义

这是一个必须明确实现的规则：

1. 用户只创建了一级分类时，该一级分类必须能直接被用作流水类别
2. 如果后续用户在这个一级分类下面新增了子分类，则之前直接挂在该父类的流水不能丢失
3. 后续做该一级分类内部的子类占比统计时，之前直接挂在父类之上的流水应归入一个特殊项："未分类"

### 这个规则存在的原因

为避免两个问题：

1. 用户只创建父类但没有子级时，无法选分类
2. 用户后续新增了子级之后，原来挂父类的流水在统计时"无处归属"

# 7. 状态管理与本地存储策略

## 7.1 推荐结构

使用一个中心 `LedgerStore` 统一管理：

- 业务数据
- OCR 结果
- Dashboard 统计
- Apple 登录状态
- iCloud 同步状态
- 冲突处理状态

## 7.2 启动流程

App 启动后建议按以下顺序：

1. 读取 Apple 登录缓存
2. 校验 Apple 凭证是否有效
3. 检查是否启用云同步
4. 读取本地快照
5. 如果本地无数据，则导入默认种子数据
6. 重新计算统计派生
7. 如果开启云同步，尝试智能同步
8. 刷新首页 Dashboard 数据

## 7.3 本地持久化原则

每次用户执行新增 / 修改 / 删除流水、分类、账本，或创建预算，都应立刻保存本地快照。

## 7.4 持久化与同步顺序

正确顺序：

1. 改内存状态
2. 刷新派生数据
3. 写本地快照
4. 如已开启云同步，再尝试同步到 CloudKit

# 8. 首页概览设计

文件建议：`DashboardView.swift`

## 8.1 页面目标

首页不是流水列表，而是汇总看板：时间维度统计、分类占比、趋势分析、预算摘要。

## 8.2 页面结构

从上到下建议为：

1. 统计筛选区
2. 汇总卡片区
3. 分类占比区
4. 收支趋势区
5. 分类变化趋势区
6. 预算摘要区

## 8.3 顶部标题栏

- 标题："概览"
- 右上角按钮：日期快捷 / 日历、刷新按钮（重新刷新 Dashboard 数据）

## 8.4 首页筛选设计

首页只保留轻量切换，必须支持：

- 本周
- 本月
- 本年

不能把复杂筛选放在首页（用户要求首页更清爽，精准筛选应放到流水页）。

## 8.5 时间范围显示

首页应显示当前统计范围，例如 `2026-09-01 ~ 2026-09-30`，并支持点击后打开"时间范围选择 Sheet"。

## 8.6 置顶时间范围

需要支持自定义时间范围并置顶，用于用户常看的特殊统计窗口。建议功能：

- 常用范围：本周 / 本月 / 本年
- 已置顶时间范围列表
- 新增一个自定义范围并命名置顶
- 左滑删除已置顶

## 8.7 汇总卡片

必须展示：

1. 总支出
2. 总收入
3. 结余
4. 预算剩余

## 8.8 分类占比图

支持两种展示形态：

- 饼图 / 环图
- 柱状图

切换方式：点击图表区域切换。右上角提供一个筛选器：

### 筛选规则

- 全部大类
- 某个一级分类

### 统计含义

- 全部大类：按一级分类看总支出占比
- 某个一级类：看这一级类下的子类占比

### 特别规则

# 16. OCR 识图记账设计

## 16. OCR 识图记账设计

文件建议：

- `OCRImportService.swift`
- `ReceiptParser.swift`
- `OCRImportPreview.swift`
- `ExportReceiptView.swift`

## 16.1 页面目标

从支付宝 / 微信截图中识别账单并生成待确认的流水。

## 16.2 整体流程

```
A(用户选择图片) -> B(Vision OCR 提取文本)
  / 或 B(VNRecognizeTextRequest -> topCandidates(1))
C(单据规则解析 ReceiptParser)
D(展示结果多条目)
D -> E(用户确认并补字段)
E -> F(用户勾选多笔批量保存)
G -> H(保存为流水)
```

## 16.3 支持的图片类型

至少支持：

1. 微信转账 / 支付详情页
2. 支付宝支付详情页
3. 支付宝账单列表页
4. 通用账单详情页
5. 通用列表页

## 16.4 OCR 服务层要求

使用 Vision 提取图片文本。

### 设置建议

- 识别等级：准确优先
- 中文简体 + 英文
- 支持语言修正
- 支持混淆修正

### 建议实现参数

```swift
let request = VNRecognizeTextRequest { request, error in
}
request.recognitionLevel = .accurate
request.usesLanguageCorrection = true
request.recognitionLanguages = ["zh-Hans", "en-US"]
```

### 输出结构

OCR 服务层本身只负责把图片变成一段按行拼接的字符串：

```
text
line1
line2
line3
```

后续真正的"账单理解"逻辑由 `ReceiptParser` 负责。

### 16.4.1 OCR 服务层伪代码

```swift
func recognizeText(from image: UIImage) async throws -> String {
    guard let cgImage = image.cgImage else { return "" }

    return try await withCheckedThrowingContinuation { continuation in
        let request = VNRecognizeTextRequest { request, error in
            if let error {
                continuation.resume(throwing: error)
                return
            }

            let observations = request.results as? [VNRecognizedTextObservation] ?? []
            let lines = observations.compactMap { $0.topCandidates(1).first?.string }
            continuation.resume(returning: lines.joined(separator: "\n"))
        }

        request.recognitionLevel = .accurate
        request.usesLanguageCorrection = true
        request.recognitionLanguages = ["zh-Hans", "en-US"]

        let handler = VNImageRequestHandler(cgImage: cgImage, options: [:])
        do {
            try handler.perform([request])
        } catch {
            continuation.resume(throwing: error)
        }
    }
}
```

## 16.5 解析器总体设计

解析器建议命名为：`ReceiptParser`。职责不是金额分析，而是：

1. 规范化 OCR 文本
2. 判断截图类型
3. 根据页面类型走不同解析分支
4. 提取金额 / 标题 / 商户 / 时间 / 支付渠道 / 分类建议
5. 输出单笔或多笔 `OCRImportResult`

### 当前推荐入口函数

```swift
func parse(rawText: String) -> OCRImportResult
func parseMultiple(rawText: String) -> [OCRImportResult]
```

其中 `parse(rawText:)` 返回单笔最终结果，`parseMultiple(rawText:)` 尝试解析出多笔列表。

### 16.5.1 页面类型判断顺序

```swift
func parse(rawText: String) -> OCRImportResult {
    let lines = normalizedLines(from: rawText)

    if isWeChatTransferDetailPage(lines: lines) {
        return parseWeChatTransferDetail(lines: lines)
    }
    if isAlipayDetailPage(lines: lines) {
        return parseAlipayDetails(lines: lines)
    }
    if isListPage(lines: lines), let first = parseMultiple(lines: lines).first {
        return first
    }
    if let first = parseMultiple(rawText: rawText).first {
        return first
    }
    return parseFallback(lines: lines)
}
```

### 为什么顺序不能乱

1. 微信转账详情页结构最具特征
2. 支付宝详情页有自己的稳定字段
3. 列表页通常与详情页容易混淆
4. 列表页如果过早 fallback，会丢失多笔拆分能力

### 16.5.2 文本预处理规则

```swift
private func normalizedLines(from rawText: String) -> [String] {
    rawText
        .split(whereSeparator: { $0.isNewline })
        .map { normalizeLine(String($0)) }
        .filter { !$0.isEmpty }
}
```

#### 行清洗细节

建议做以下替换：

- `，` `/` `、` 统一替换为 `.`
- 某些 OCR 错误格式如 `￥78-00` 替换为 `￥78.00`
- 去掉首尾空白

目的是让金额、时间、符号识别更稳定。

### 16.5.3 页面类型判断规则

#### A. 微信转账详情页

判定特征建议：存在"零钱明细"，同时存在"付款方式"或"收款方备注"。

```swift
private func isWeChatTransferDetailPage(_ lines: [String]) -> Bool {
    lines.contains(where: { $0.contains("零钱明细") }) &&
    lines.contains(where: { $0.contains("付款方式") || $0.contains("收款方备注") })
}
```

#### B. 支付宝详情页

判定特征建议：存在"账单详情"，同时存在"收/支分析"。

#### C. 通用详情页

判定方式建议基于字段命中数，而不是单一关键词。内置一组 detail labels：

- 当前状态、支付时间、商品、商品说明、商户全名、收单机构、支付方式、付款方式、支付渠道、交易单号、订单号、商户单号、优惠、原价、收款方、收款方备注、交易对方、商家、转账时间、转账单号、零钱余额、扣款说明

当这些字段命中数 >= 4 时，可视为 detail page。

#### D. 支付宝列表页

判定特征建议：存在"全部交易记录"，存在"收/支分析"。

## 16.6 字段提取规则

### 16.6.1 金额提取

金额提取不能只用一个正则完事，要分场景。

#### 层 1：强特征金额

优先从这些行里取：包含 `¥` 或 `￥`，但不包含原价 / 优惠 / 余额，并满足：

```
-?\¥?\s*\(?￥?\d+(?:\.\d{1,2})?\)
```

#### 层 2：通用 fallback 金额

满足所有行，给候选金额打权重：

- 含：支付 / 支出 / 收款 / 收入 / 实付 / 合计 / 加分
- 含负号加分
- 含 `￥` / `¥` 加分
- 若是"账单 / 零钱明细"等强调行得分

最后选最高权重金额。

#### 金额提取关键正则

```regex
-?\¥?\s*\(?￥?\d+(?:\.\d{1,2})?\)
```

```regex
-?\d+(?:\.\d{1,2})?
```

前者用于取绝对金额，后者用于判断列表页金额正负号。

### 16.6.2 收支类型判断

建议组合判断，不只看正负号。

#### 文本关键词

收入关键词：收入、收款、退款、入账、到账、转入。
支出关键词：支出、付款、支付、消费、扣款。

#### 规则建议

1. 如果文本出现"付款 / 支出 / 支付成功 / 扫码付款"，优先判支出
2. 如果出现"收款"且没出现"付款"，优先判收入
3. 列表页金额有负号，则判支出
4. 最后再 fallback

### 16.6.3 时间提取

建议支持至少这些格式：

- `yyyy年M月d日 HH:mm:ss`
- `yyyy年M月d日 HH:mm`
- `yyyy-MM-dd HH:mm:ss`
- `yyyy-MM-dd HH:mm`
- `M月d日 HH:mm`

如果是 `M月d日 HH:mm`，需要补上当前年份。

### 16.6.4 支付渠道提取

建议优先从字段映射中读取：支付方式、付款方式、支付渠道。如果字段不存在，再从整页行里找：花呗、银行卡、信用卡、储蓄卡、微信零钱、支付宝余额、微信支付、支付宝、云闪付。

建议保留一个 `normalizePaymentMethod(_ raw: String)`，要做的事：

- 去掉字段名："支付方式" / "付款方式" / "支付渠道"
- 去掉 `：` `：` 这类分隔符
- 清理首尾空格
- 做常见映射：
  - 包含"微信零钱" → `微信零钱`
  - 包含"支付宝余额" → `支付宝余额`
  - 包含"微信支付" → `微信支付`
  - 包含"花呗" → `花呗`
  - 包含"云闪付" → `云闪付`
  - 包含"信用卡" / "储蓄卡" / "银行卡" → 保留更完整文本

### 16.6.5/7 商户与标题提取

#### 通用详情页商户优先级建议

1. 商户全名
2. 收款方
3. 交易对方
4. 第一个像用户名的文本行

#### 通用详情页标题优先级建议

1. 页面头部第一个看起来像标题的行
2. 商品
3. 商品说明
4. merchant

#### 列表页标题规则

列表页标题往往直接就是商户名或简化交易名。如果出现"付款-某某商家""转账给某某"，可进一步提取 merchant。

### 16.6.8 原价与优惠提取

建议显式提取。来源可以是：

1. 字段中的对应字段
2. 原价行
3. 行内同时出现"优惠 + 金额"的行

建议保留一个 `makeFieldMap(lines:)`：

```swift
["原价": ...]
["优惠": ...]
["备注": ...]
```

映射成字段。

## 16.7 字段映射表策略

因为详情页经常这样：

```
支付时间
2026-09-05 12:00:00
```

而不是 `支付时间：xxx` 一式。

### 解析要求

要同时支持两种格式：

1. 标签一行，值一行
2. 标签和值同一行，例如：`支付时间：2026-09-05 12:00:00`

### 作用

（见上）

## 16.8 微信转账详情页解析细节

### 典型特征

- 页面里有"零钱明细"
- 有：转账时间
- 有：收款方备注
- 有：支付方式
- 有：转账单号

### 建议解析逻辑

1. 先构建 `fieldMap`
2. 再调用专门的 `extractWeChatTransferFieldValue(label:lines:)`
3. 从页面的"值区块"里按 label 分别取值

### 推荐细节字段

- 当前状态
- 收款方备注
- 金额行
- 支付方式
- 转账时间
- 转账单号

### kind 判定

微信转账页可能是付款也可能是收款，建议组合：标题文本、页面整体文本、未判定。

## 16.9 支付宝详情页解析细节

### 典型特征

- 页面里有：账单详情
- 有"付款方式"或"扣款说明"

### 建议提取的特化字段

- `paymentMethod`：从含"花呗 / 银行卡 / 支付宝余额 / 储蓄卡"的行识别
- `merchant`：优先交易详情 / 淘宝 / 天猫等平台行
- `title`：从"交易详情"后面一致两行推出标题
- `deduction note`：提取"先用后付 / 芝麻分"等扣款说明

### 明细 details items 建议

- 支付时间
- 付款方式
- 扣款说明

## 16.10 支付宝列表页解析细节

### 为什么要单独写一套逻辑

支付宝列表页不是单笔详情，而是：按月分段，每笔下面有多笔交易。

### 推荐分段逻辑

1. 识别月份头，例如 `2026年9月` 或 `9月`
2. 把每个月的行聚成一个 section
3. 对每个 section 再解析交易项

### 围绕日期行找

- 前面若干行里找标题
- 前面若干行里找 category
- 前面若干行里找 provider
- 就近行里找金额

### 日期正则建议

```regex
^\d{4}-\d{2}-\d{2}$
```

```regex
^\d{1,2}月\d{1,2}日$
```

### 月份头正则建议

```regex
^\d{4}年(\d{1,2})月$
```

```regex
^(\d{1,2})月(.*)?$
```

## 16.11 通用列表页解析细节

### 基本思路

1. 清理噪音行
2. 识别月份头
3. 识别标题行
4. 识别日期行
5. 把日期行按顺序对齐到记录

### 标题行判断建议

满足：包含中文或英文字母、不是噪音行、不是金额行、不是月份头、不含明显年份标记。

### 日期行判断建议

```regex
^\d{1,2}月\d{1,2}日\s+\d{1,2}:\d{2}$
```

## 16.12 噪音过滤规则

建议保留两套噪音过滤：

### 通用噪音

- 账单、零钱明细、账单服务、申请电子凭证
- 单独的数字、纯时间点位、单字符行

### 支付宝列表页噪音

- 搜索交易记录、全部、支出、转账、退款、收入
- 收支分析、本月已省、账单月报、等待确认收货

## 16.13 分类建议词典

建议保留一个明确的 `rules` 数组，每条规则包含：`keyword`、`tokens`、`path`。例如：

```swift
.init(keyword: "奶茶咖啡", tokens: ["瑞幸", "库迪", "星巴克", "咖啡", "奶茶"], path: ["餐饮", "奶茶咖啡"])
```

### 分类置信度建议

对每条规则统计 token 命中数：

```swift
score = 命中 token 数
confidence = min(0.50 + Double(score) * 0.12, 0.95)
```

### 收支校正

如果当前识别出的 `kind == expense`，但分类路径第一层是"收入"，则应校正处理：清空分类建议，或改置置信度低。防止把支出误判成收入类。

## 16.14 OCR 结果置信度设计

不要固定写一个值，建议按字段完整程度估算：

- 有金额加分
- 有商户加分
- 有分类建议加分
- 特定页面类型可提高基础分

例如：微信转账详情 0.96、支付宝详情 0.95、列表页 0.87–0.98，fallback 按命中信息动态估算。

## 16.15 OCR 结果展示与保存

### 单笔模式

展示：金额、类型、标题、商户、支付路径、时间、原价、优惠、分类建议、置信度、明细字段。下方显示"确认入账"按钮。

### 多笔模式

显示识别结果列表，用户可勾选多条，再批量保存。

### 重要要求

识别结果默认只是"候选草稿"，不能直接自动落库。**必须先确认再入账。**

## 16.16 OCR 结果转流水草稿的建议实现

建议提供：

```swift
init(parsed: OCRImportResult, source: String = "ocr")
```

初始化时自动带入：title、amount、kind、happenedAt、paymentMethod、merchant、source = "ocr"、originalAmount、discountAmount。然后再调用：分类建议匹配、用户手动补充账本 / 分期 / 备注。

## 16.17 OCR 模块给另一个 AI 的最低实现要求

如果另一个 AI 无法 100% 还原全部代码，最低也必须保证：

1. 有独立的 OCRService (Vision)
2. 有独立的 ReceiptParser
3. 区分"详情页解析"和"列表页解析"
4. 能识别支付渠道
5. 能识别时间
6. 能生成分类建议
7. 结果先确认后入账

## 16.6 解析器要求（补充）

不基于当前截图硬编码编程，而应采用：

- 关键字段匹配
- 文本模式匹配
- 平台特征判断
- 时间 / 金额正则
- 支付渠道关键词识别
- 分类关键词词典匹配

## 16.6 单笔识别页面

必须展示：金额、类型、标题、商户、支付路径 / 支付渠道、时间、原价、优惠、分类建议、置信度、明细字段。

## 16.7 多笔识别页面

用列表展示每一笔：每笔可勾选，顶部可支持全选，可批量保存。

## 16.8 OCR 后的保存策略

### 必须先确认再入账

这是强要求。不能识别后直接自动写流水。用户可修改字段：标题、金额、类型、时间、分类、账本、支付渠道、分账信息、商户、备注。

## 16.9 分类建议规则

建议内置一个规则词典，例如：

- 瑞幸 / 星巴克 / 奶茶 / 咖啡 → 餐饮 / 奶茶咖啡

# 18. Apple 登录与 iCloud 同步设计

## 18.1 Apple 登录的定位

Apple 登录当前不是用来做后端鉴权，而是用于 App 内展示用户身份，为未来扩展留接口。

## 18.2 iCloud 同步的定位

CloudKit 才是真正的云同步实现。当前建议使用"整包快照同步"。

一个固定 Record：名字 `ledgerSnapshot`，Record 中包含整个账本快照 JSON。

### 优点

- 实现简单
- 本地优先容易落地
- 不阻塞功能推进

### 缺点

- 粒度较粗
- 冲突处理不够细

## 18.3 同步模型

（同上）一个固定 Record：名字 `ledgerSnapshot`，Record 中包含整个账本快照 JSON。

## 18.4 智能同步规则

1. 读取本地快照
2. 拉取云端快照
3. 比较 `updatedAt`
4. 决定：
   - 云端新 → 拉本地
   - 本地新 → 推云端
   - 时间接近且内容不同 → 进入冲突

## 18.5 冲突处理设计

当前即可采用"用户二选一"：保留本地 / 采用云端。不要求实体级 merge。

# 22. 关键边界条件与异常处理

## 22.1 分类相关

- 没有分类时：允许保存为"未分类"
- 只有一级分类：可直接用作流水类别
- 新增子类后：原父类流水归入"未分类"项，不丢失

## 22.2 账本相关

- 没有账本时：流水仍可正常保存
- 账本删除：只移除账本，不能删掉流水本体
- 流水关联多个账本：标签简化展示

## 22.3 分期相关

- 分期开关关闭：不显示分期字段
- 分期月数 <= 1：视为不分期

## 22.4 多人分账相关

- 未开启多人分账：分账 UI 不显示
- 开启了分账但未选成员：保存时校验拦截

## 22.5 OCR 相关

- OCR 识别失败：允许手动输入
- 置信度过低：提示用户核对

## 22.6 云同步相关

- iCloud 不可用：App 仍可完整使用
- 冲突时：用户二选一，不做自动 merge

## 22.7 背景图相关

- 背景图存在时：卡片使用半透材质，保证文字可读
